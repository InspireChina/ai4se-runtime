# 愿景 × 蓝图 × 现实：实用对照与中肯建议

> 写给：想做「可适配、可扩展、多语言、多项目可集成」的 AI 工程底座，且已经被 ai-loop 式无人值守脚本伤过的人。  
> 性质：实用判断，不是 Frozen 架构；不否定蓝图方向，只区分 **能落地 / 半能落地 / 愿望清单**。  
> 日期水位：对照当前仓库至 Sprint-7。

---

## 0. 先用一句话说清你真正想要的

你要的不是「又一个会聊天的 Coding Agent」。

你要的是：

> **一套工程运行时底座（Runtime / Platform Kit）**：  
> 不同项目可以集成进来；后端 Java 或其他语言、前端同样可插；  
> 按项目特点补 Worker / 规则 / 测试 / 知识，而不是每个项目从零另起一套脚本神话。

同时，你已经被现有 ai-loop 伤到的点，本质是：

| 痛点 | 本质 |
|------|------|
| skills/rules 太多且不强制 | **治理假象**：有文档无执行 |
| 0→1 没长远性 | **没有可延续的工程状态**（只有当次对话产物） |
| 续作/摸底弱、知识库弱 | **缺少可检索的 Artifact + 代码事实源** |
| 质量差、前后端扯皮 | **缺少契约产物与验证门禁** |
| 测试不知道接什么 | **测试未被当成一等 Worker/门禁** |
| 自动进化 | **最高难**：没有稳定评价闭环就谈进化=自嗨 |

下面按「蓝图能扛多少」说实话。

## 1. 总判断（先看结论）

| 类别 | 占比感（主观） | 含义 |
|------|----------------|------|
| **蓝图里可实现、且值得做** | ~35% | Task/Artifact/Worker/Context/Trace/Checkpoint（窄）、可插拔执行 |
| **蓝图里半可实现（要大幅裁剪才真）** | ~30% | 规则强制、知识摸底、质量门禁、测试集成、多语言适配 |
| **基本是美好愿望清单（现阶段）** | ~35% | 自动进化、全自动 0→1 且长远、skills 海洋自治、前后端职责 AI 自动分对 |

更刺一句：

> **你的蓝图「形状」适合做平台底座；  
> 但蓝图「厚度」（Scheduler+Workflow+Capability+Plugin+Knowledge+Evolution 一次上齐）不适合当施工清单。  
> 你真正该买的是「可强制的薄平台」，不是「会自己变聪明的大脑」。**

当前仓库已经踩在正确薄平台上：工单、产物、工人、录像、存档点（能写）、真命令工人。  
**还没碰到你最痛的：强制、摸底、质量、测试、续作。**

## 2. 逐条对照：痛点在蓝图里是什么命运？

### 2.1 Skills / Rules 过多，且很多不强制遵守

| | |
|--|--|
| **蓝图怎么说** | Rule / Skill / Capability / Policy 例外 |
| **现实** | 文档层很全；代码层 **几乎没有强制执行器** |
| **可实现性** | **半可实现** |
| **中肯做法** | 规则分三级：① 必须机器拦（测试/lint/契约检查 Worker）② 必须人审 ③ 仅建议。**删掉或降级「只写不跑」的 skills**。没有执行器的 rule = 愿望。 |
| **愿望部分** | 「很多 skills 自动被遵守」——不会；只会「少数门禁真的挡住合并/完工」。 |

**建议：** 别再扩 skills 目录。先选 **3～5 条**能写成自动检查的（例如：OpenAPI 变更必须前后端同 PR；禁止无测试的公共 API）。用 Worker 跑检查，失败则 Task FAILED。这才叫治理。

---

### 2.2 分析需求 / 0→1 搭建没有长远性

| | |
|--|--|
| **蓝图怎么说** | Workflow、Iteration、Profile、Checkpoint |
| **现实** | 有 Task/Checkpoint 雏形；**没有「长期产品决策」载体** |
| **可实现性** | **半可实现（靠产物，不靠灵感）** |
| **中肯做法** | 把「长远性」落成 **必须入库的 Artifact**：愿景摘要、边界非目标、模块划分、接口草图、ADR。下次开 Task **强制读取这些 ArtifactId**，禁止只读聊天记录。 |
| **愿望部分** | AI 一次 0→1 就自然长远——不成立。长远来自 **约束与遗产产物**，不是模型情商。 |

**建议：** 平台不负责「想得远」，负责 **「不丢决策」**。长远性 = Artifact 遗产 + 新 Task 的输入契约。

---

### 2.3 不从 0→1、续作新功能；基于代码/知识库摸底弱

| | |
|--|--|
| **蓝图怎么说** | Knowledge、Repo Graph、ExecutionContext 视图 |
| **现实** | **最弱的一环之一**；几乎未实现 |
| **可实现性** | **可实现，但是慢功夫**；不是一个 Sprint 的愿景暴涨 |
| **中肯做法** | 知识库不要先上「智能」：先上 **可检索事实**——目录树、关键模块说明、接口列表、上次失败 Trace、既有 Artifact。Worker：`RepoInventoryWorker` / `TestMapWorker` 之类只读采集。 |
| **愿望部分** | 「知识库一建就能彻底摸底需求」——摸底永远不彻底；只能 **提高召回与可审计引用**。 |

**建议：** 把「摸底」定义成交付物：`requirements-hit-set` Artifact（引用了哪些文件/接口/历史 ADR），没有引用表不许进入编码 Worker。

---

### 2.4 代码质量差、跑批脆、兼容性差、前后端职责乱

| | |
|--|--|
| **蓝图怎么说** | Artifact 契约、Quality Gate、Verify 阶段、Rule |
| **现实** | 有 Artifact 模型；**没有质量门禁流水线** |
| **可实现性** | **高度可实现（且最该做）** |
| **中肯做法** | 质量不是「写得漂亮」，是 **过不去门就失败**：编译、单测、契约测试、OpenAPI diff、基础 lint。前后端乱 = **缺共享契约 Artifact**（API schema / 事件 schema），不是缺更多 prompt。 |
| **愿望部分** | AI「自动知道」这段该前端还是后端——不可靠。要靠 **任务模板 + 契约归属字段**（这个变更的 owner=backend|frontend|both）。 |

**建议：** 平台下一阶段的「扩展点」优先做 **Verify Workers**，而不是更多 Coding Workers。

---

### 2.5 测试自动化不知道接什么，如何保证功能完整

| | |
|--|--|
| **蓝图怎么说** | Verify、质量门、可插拔 Capability |
| **现实** | 未集成项目级测试策略 |
| **可实现性** | **可实现；且必须按项目适配，不能全球一套** |
| **中肯做法** | 测试不是选「最强框架」，是选 **和仓库已有栈一致** 的最小集：Java→Surefire/Failsafe；前端→项目已有 Vitest/Jest/Playwright；接口→契约测试。平台只定义：**Verify 阶段必须跑哪些 Worker、失败如何使 Task 失败**。 |
| **愿望部分** | 一个万能测试引擎适配一切项目——假。 |

**建议：** 每个接入项目写一份 `Project Test Profile`（就是你们 Profile 思想的瘦版）：  
`unit` / `api` / `e2e(可选)` 三条命令。Runtime 只负责调度这些命令 Worker 并收集日志 Artifact。

---

### 2.6 自动进化

| | |
|--|--|
| **蓝图怎么说** | 各类 Reflect / Evolution / 持续改进叙事（归档里常见） |
| **现实** | **愿望清单头部** |
| **可实现性** | **长期 theoretically 可能；短期 practically 不该进主路径** |
| **中肯做法** | 进化 = 改规则/改 Worker/改门禁的 **受控变更 Task**，必须有指标（失败率、回滚、测试红灯）。没有指标的进化 = 随机改 prompt。 |
| **愿望部分** | 系统自己越跑越强、无人看管——在治理都未强制前，这是幻觉。 |

**建议：** 用词改成 **「受控改进」**，从词汇上降低预期；真正的自动进化至少排到：强制门禁 + 测试闭环 + 可回放 Trace 之后。

## 3. 「多语言、多前端、多项目可集成」——蓝图里有多少是真的？

### 3.1 可实现的部分（值得坚持）

你要的「可适配可扩展」，在工程上正确翻译是：

```text
稳定内核契约（Task / Artifact / Context / Worker SPI / Trace / Checkpoint）
        ↑
   各语言 Worker / 适配器（Java、Node、Python、Go…）
        ↑
   各项目 Profile（命令、门禁、工作区、测试套件）
```

这意味着：

- **Kernel 保持语言中立的思想**（甚至未来可用 IDL/JSON 描述 Task/Artifact 事件）  
- **执行用 Worker 插**：Java 项目接 Java 测试 Worker；前端接 Node Worker；都不必进 Kernel  
- **项目差异进 Profile / 配置，不进内核 if-else**

当前仓库用 Java 实现 Kernel+Engine **并不妨碍**这个目标——前提是：**别把项目业务写进 Kernel**。你们基本做到了。

### 3.2 半可实现（要设计克制）

- 「前端同样」：前端不该嵌进 Kernel；应是 **Frontend Verify/Build Worker** + **契约 Artifact**。  
- 「其他语言后端」：短期 **多语言 Worker 进程**（CLI/HTTP）比「Kernel 多语言重写」现实 100 倍。  
- 「完善即可开发其他项目」：**集成成本不会为零**；成功标准应是「一周内接到门禁可跑」，不是「零配置神器」。

### 3.3 愿望清单

- 一套蓝图自动生成任何技术栈的正确前后端分工  
- 不改项目、只「集成一下」就无人值守高质量交付  
- 知识库自动理解所有历史决策并保证不偏航  

这些需要组织流程 + 长期数据，不是多画几个框能解决。

## 4. 蓝图清单：哪些该留、哪些该降级、哪些该冷冻

### 4.1 必须留（平台真骨头）

- Task（工单）  
- Artifact（唯一跨阶段货币）  
- ExecutionContext（执行期可视边界）  
- Worker SPI（一切副作用出口）  
- Trace（可回放）  
- Checkpoint（先写后恢复，恢复单独里程碑）  
- Invariants（少而硬）

### 4.2 该降级成「项目配置 / Worker」而不是内核对象海

- Skills → **可选提示包**，默认不强制  
- Rules → **少数可执行门禁** + 大量建议  
- Knowledge → **先索引与引用，后智能检索**  
- Workflow → **先固定阶段模板**（Analyze → Change → Verify），后 DSL  
- Plugin → **先手动组装 Worker**，后插件市场  

### 4.3 该冷冻（写进北极星，不排期）

- 自动进化  
- 完备 Scheduler 中枢（在单 Worker 都未多步骤前）  
- 万能 Agent 大脑  
- 「规则很多且都遵守」的治理宇宙

## 5. 实用中肯建议（按你该怎么做，而不是怎么画）

### 建议 1：改产品口号（避免自己骗自己）

不要说：

> 无人值守自动进化的 AI 软件工厂  

改成：

> **可集成的工程 Runtime：用 Task/Artifact/Worker 把「改代码、跑检查、留证据」强制串起来。**

这和 ChatGPT 蓝图不矛盾，只是把销售词从「神话」改成「基建」。

### 建议 2：用「三个强制」代替「一百个 skill」

每个接入项目只先强制三件事：

1. **改动必须产生契约/说明类 Artifact**（至少一种）  
2. **Verify Worker 必须跑绿**（项目自己的测试命令）  
3. **失败必须留 Trace + 失败产物**（可回放）

skills/rules 超过这个集合的，全部降级为「可选」。

### 建议 3：平台扩展点优先级（未来 3～6 个月）

```text
P0  Verify/Test Workers（接项目已有命令）
P0  契约 Artifact（API/事件/页面边界）
P1  只读 Repo/知识采集 Worker（摸底用）
P1  Checkpoint 政策 + 以后再 Resume
P2  多步骤模板（仍可不做完整 Scheduler）
P3  多语言 Worker 宿主（进程/HTTP）
P∞  自动进化、庞大 Rule 宇宙、Claude 神话
```

### 建议 4：多语言策略要「外包执行，不外包内核」

- 短期：Kernel/Engine 继续 Java（或任一主力语言）  
- 扩展：Worker 用 **任意语言可执行文件**，经 SPI/CLI 回报 `WorkResult` JSON  
- 前端：永远是 Worker + 契约，不进 Kernel  

这是实现「Java 或其他语言都能接」的唯一现实路径。

### 建议 5：对 ai-loop 脚本的处理态度

现有脚本可以当 **临时 Worker 原型**，但必须迁到：

- 明确 Task  
- 明确输入 Artifact  
- 明确输出 Artifact  
- 明确失败码  

否则脚本永远是「能跑但不治理」。

### 建议 6：成功标准要可测

集成一个新项目，两周后只问四个问题：

1. 能否提交 Task 并看到 Trace？  
2. 能否跑项目自己的测试门禁并挡住烂代码？  
3. 能否留下 API/需求/变更说明 Artifact 供下次续作？  
4. 前后端变更有没有共享契约，而不是靠嘴分活？  

这四个「是」，你的底座才算开始赚钱；否则蓝图再全也是愿望。

## 6. 直接回答你的三个问题

### 「有多少可实现？」

- **底座形态（可适配、可扩展、多项目集成）**：可实现。  
- **强制质量与测试门禁**：可实现，且最该做。  
- **续作与摸底**：可实现，但靠 Artifact/索引，不是靠更大模型幻觉。  
- **多语言**：可实现，靠 Worker 宿主，不靠重写世界。

### 「有多少是愿望清单？」

- skills/rules 又多又都遵守  
- 0→1 自动长远  
- 知识库一次建好就摸底彻底  
- AI 自动分清前后端且总对  
- 自动进化  

### 「最中肯的建议是什么？」

> **把 ChatGPT 蓝图从「全能工厂施工图」降级为「北极星」；  
> 把平台做成「少而硬的强制管线」：Task → 变更 → 契约产物 → 测试门禁 → Trace/Checkpoint；  
> 用 Worker 承接项目差异与多语言；  
> 先治你已经被 ai-loop 伤害的那几刀（强制、摸底、质量、测试），再谈进化。**

你们现在仓库的水位（真 ShellWorker + 干净 Kernel）说明：**方向没走歪**。  
危险只在一点——**若下一阶段又按愿望清单加 Scheduler/Plugin/Evolution，会重新变成「skills 很多但不强制」的升级版。**

## 7. 一页纸决策（可贴墙）

| 要 | 不要 |
|----|------|
| 少规则，真门禁 | 多 skills，假遵守 |
| Artifact 遗产续作 | 只靠聊天记忆 |
| Verify Worker 接项目测试 | 空想万能测试引擎 |
| Worker 多语言扩展 | Kernel 多语言重写 |
| 固定阶段模板 | 过早 Workflow DSL |
| 受控改进 | 自动进化叙事 |
| 对外讲「工程 Runtime」 | 对外讲「全能无人值守大脑」 |
