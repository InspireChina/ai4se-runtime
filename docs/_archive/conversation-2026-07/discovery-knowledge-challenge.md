# 挑战应答：需求摸底 × 知识库 —— 可靠吗？怎么建才不拖死？

> **挑战原意：** 摸底要省 token；要借鉴已落地开源思想（图/节点等）；知识库如何划分、建什么、什么是无效建设；蓝图/通路手册这一步靠不靠谱；是否贴合真实迭代；还有哪些容易踩的坑。  
> **态度：** 接受挑战。先前 `serial-pipeline` / `build-pathway` 对 **S8 摸底+知识** 写得**不够硬**——方向对，但粒度停留在「先树+grep+分桶」，若按字面扩张，确实可能建成理论空洞。  
> **本文目的：** 把这一环补到「可执行、可证伪、可维护预算」的程度。

---

## 0. 直接回答你的四连问

| 问题 | 直答 |
|------|------|
| 通路手册这一步我会怎么做？ | **拆开**：先「按需检索式摸底」，后「极瘦知识层」；禁止一上来建全能知识图谱。 |
| 可靠么？ | **窄定义下可靠**（事实召回+缺口清单）；**宽定义不可靠**（理解业务、保证长远）。 |
| 思考完善了么？ | **之前不够完善**——本文是补课。 |
| 贴合真实项目迭代么？ | **贴合「变更驱动」迭代**；不贴合「先建完百科再开发」。真实团队也是变更时才更新相关知识。 |

## 1. 先定死：摸底在解决什么问题？

摸底 **不是**「把仓库读进模型脑子」。  
摸底是：

> 为 **这一次需求** 生成一份 **可审计的证据包**：  
> 可能相关的代码/契约/历史决策在哪、不知道什么、乱动可能伤到什么。  
> 并且 **尽量少烧 token**。

若目标变成「建立永久正确的企业知识大脑」——那是另一个产品，失败率极高，且会拖垮维护。

---

## 2. 开源里真正「热且落地」的思想（可借鉴 vs 别神化）

下面只借 **已被验证的机制**，不借「整仓复刻」。

### 2.1 值得借鉴（省 token、可推广）

| 思想来源（类型） | 落地要点 | 借到我们摸底里 |
|------------------|----------|----------------|
| **Aider Repo Map** | 不塞全仓；用结构摘要 + 重要性排序，只暴露「地图」 | `discovery.repo-map` = **压缩地图**，不是文件全文 |
| **代码智能图（SCIP/LSIF、语言服务器、依赖图）** | 节点=符号/文件，边=引用/依赖；查询精确 | 「图」优先用于 **精确跳转**，不是给 LLM 讲故事 |
| **Search-first（Sourcegraph / ripgrep / 语义检索可选）** | 先检索再读文件 | 摸底流水线：**检索 → TopK → 定点读** |
| **ADR / TechDocs / 目录化文档** | 决策写成短文+状态；随变更更新 | 知识主力是 **ADR 与契约**，不是聊天纪要 |
| **软件目录（Backstage 类）** | 服务/Owner/文档链接的薄目录 | Profile + 模块 Owner 表，极瘦 |
| **渐进披露（工具/技能描述）** | 先短描述，需要再展开 | 知识条目：摘要常驻，正文按需加载 |
| **CI 产物当事实** | 测试报告、覆盖率、OpenAPI 生成物 | 「活知识」来自流水线 Artifact，不是手抄 |

### 2.2 容易神化、一建就痛的

| 想法 | 为什么痛 |
|------|----------|
| 全量向量库「永久记忆仓库」 | 漂移快、污染难洗、检索噪声大；维护成本高于收益 |
| 手维护完美领域本体/超大知识图谱 | 开发迭代速度远快于图谱更新 → **文档腐烂** |
| 「所有 skills 都是知识」 | 与代码脱节，变成第二个愿望清单 |
| 每次需求全仓 embedding | token/钱/时间爆炸，且对小改动无必要 |
| 用 LLM 定期「总结整个系统」 | 幻觉沉淀成「认证知识」= 系统性事故 |

**借鉴原则：** 借「地图 + 检索 + 精确图查询 + ADR」；不借「永久全知大脑」。

## 3. 知识库如何划分——三层，而不是一锅粥

### 3.1 推荐分桶（按「谁产生、多久过期、能否机器验证」）

```text
L1 活事实（Living Facts）     —— 机器可再生成，过期=重跑
L2 决策遗产（Decisions）      —— 人认证，短、稳、少改
L3 会话渣滓（Ephemeral）      —— 默认不入库；最多挂 Task 下
```

| 层 | 放什么 | 怎么建 | 维护成本 | 无效则怎样 |
|----|--------|--------|----------|------------|
| **L1 活事实** | 模块树、依赖边、OpenAPI 快照、测试命令、包管理锁文件摘要、符号引用（若有索引） | **Worker 生成**，可重复跑 | 低（自动化） | 几乎不该手维护 |
| **L2 决策遗产** | ADR、非目标、模块边界、公共坑 `do-not`、认证 lesson | **人写或人审** | 中（必须控数量） | 一膨胀就腐烂 |
| **L3 会话渣滓** | 聊天摘要、半成品分析、未验证猜测 | 默认丢弃或仅 Task 附件 | 高若入库 | **最易拖累** |

### 3.2 你们蓝图里的词怎么映射

| 蓝图词 | 落到哪一层 |
|--------|------------|
| Repo Graph | **L1**：文件/模块/依赖图（可再生） |
| Knowledge | 主要是 **L2**；检索时也可命中 L1 |
| Profile | **L1+配置**：构建/测试/路径约定（项目接入时写一次，变更时改） |
| skills/rules 长文 | **默认不是知识**；能门禁的进 Verify；其余可选提示 |

### 3.3 「无效建设」清单（建了反而受拖累）

下面这些 **先建 = 负债**：

1. **未绑定代码路径的「业务百科」**（无法用 hit-set 验证）  
2. **自动写入且自动「认证」的 LLM 总结**  
3. **超过 ~30～50 条还无人裁剪的 lesson 库**（检索变噪声）  
4. **与 Git 不同步的架构图大全**（三周后全假）  
5. **为省事把整段 Trace/聊天打进知识库**  
6. **多套重复知识**（Confluence + 仓库 docs + 向量库各一份）  
7. **「提升理解力」却无离线指标的工程**（只有感觉，无召回率/误伤率）

**判定标准（实用）：**

> 若一条知识 **90 天无人引用、也无法被脚本验证** → 删除或降为草稿。  
> 若维护它的时间 > 它节省的摸底时间 → 停建。

### 3.4 「提升仅存在于理论」的典型空洞建议（警惕）

- 「先把图谱建完备再开发」  
- 「全员写完美文档文化自然好」  
- 「上了向量检索质量自然升」  
- 「知识越多模型越稳」——常常相反（噪声↑）

## 4. 需求摸底：切实可行的算法（省 token）

### 4.1 标准六步（每次需求都跑，不做永久全量）

```text
1. Seed（种子）
   - 需求原文关键词 / 模块名 / 接口名（人可补）
   - Profile：主语言、源码根、忽略目录

2. Map（地图，小）
   - 目录树深度受限（如 3～4 层）
   - 模块列表 + 入口文件猜测（pom/package.json 等）
   → Artifact: discovery.repo-map（控制体积，如 < 8～15KB 文本）

3. Search（检索）
   - ripgrep/结构化搜索 TopN（路径+符号）
   - 可选：已有 SCIP/依赖图查询「谁引用 X」
   → 候选文件列表（尚未读全文）

4. Rank（排序，省 token 关键）
   - 路径命中、名字命中、图度数、近期 git 改动、是否在 Profile 核心包
   → TopK 文件（K=8～20，可配置）

5. Read（定点读）
   - 只读 TopK 的切片（函数/接口/DTO），禁止全文件无脑塞
   → discovery.hit-set（路径+符号+为何相关+置信度）

6. Gap & Risk（缺口与误伤）
   - 需求里出现但 hit-set 无落点的概念 → gaps
   - 高度数核心模块被命中 → risks
   → discovery.gaps / discovery.risks
```

**Token 省在哪：** 地图小、检索多、全文少、每阶段只带本阶段 Artifact。

### 4.2 「图和节点」在 v0/v1 分别做什么

| 阶段 | 节点 | 边 | 何时上 |
|------|------|-----|--------|
| v0 | 文件、模块 | 目录包含、粗依赖（import 正则） | **先做** |
| v1 | 类型/方法（SCIP 等） | 调用/实现/引用 | 有语言索引工具再做 |
| v2 | 服务/API/事件 | 消费生产 | 多服务才值得 |

**不要：** 一上来 Neo4j + 领域本体 + 事件溯源知识图谱。

### 4.3 和真实迭代三种场景的贴合

| 场景 | 摸底强度 | 知识用法 |
|------|----------|----------|
| **Bugfix** | 轻：报错栈 + 定点搜 | 几乎不读 L2 |
| **既有模块加功能** | 中：地图+TopK+相关 ADR | 引用 1～3 条 L2 |
| **0→1 新子系统** | 重：地图+边界 ADR 空则先澄清 | 先写 L2 边界，再编码 |

**通路手册修正：** S8 不能「一种摸底打天下」；Profile 里要有 `discovery.profile=light|normal|deep`。

## 5. 蓝图 vs 通路手册：这一步原来怎么写的、问题在哪、怎么改

### 5.1 原先写法的诚实评价

| 来源 | 说了什么 | 缺口 |
|------|----------|------|
| ChatGPT 蓝图 | Knowledge / Repo Graph / Profile 引擎 | 易做成「先建引擎」；缺维护预算与无效标准 |
| serial-pipeline | 树+grep+四个 Artifact | **可行但过粗**；缺排序/切片/分层知识 |
| build-pathway S8 | DiscoveryWorker + 认证分桶 | **把摸底与知识建设捆一阶**；易一次做爆 |

### 5.2 建议改写的台阶（替换原 S8）

```text
S8a 按需摸底引擎（无永久知识也能跑）—— 必须先通
S8b L1 活事实可再生索引（地图/依赖，CI 可重跑）
S8c L2 决策遗产极瘦库（ADR + do-not + 认证 lesson，有配额）
```

**解锁关系：**

- 没 S8a：禁止谈知识库价值  
- 没 S8c 配额与引用指标：禁止扩 lesson  
- 向量检索：至少 S8a 稳定且有「召回失败」案例后再试点（可选 S8d）

### 5.3 可靠性模型（你要的「可靠么」）

摸底系统的可靠，不定义为「懂业务」，定义为可测指标：

| 指标 | 含义 | 怎么验 |
|------|------|--------|
| **召回** | 后来真改到的文件，是否早在 hit-set | 事后对照 diff |
| **精确** | hit-set 里从未打开的比例 | 越低越好 |
| **缺口有效** | gaps 是否变成澄清题且被人答 | 问卷引用率 |
| **误伤提示** | risks 是否挡住乱改核心 | 回顾事故 |
| **token** | 单次摸底输入体积 | 设上限报警 |

没有这些指标，任何「知识提升质量」都是空洞。

## 6. 你没提、但非常容易犯错的地方

1. **把摸底做成编码的前置全读** → token 爆、还干扰模型。  
2. **命中列表当许可清单的反面：没命中就绝对不让改** → 过严会逼人关闸；应是「强提示+风险升级」而非死锁（可配置）。  
3. **知识认证变橡皮图章** → 人随手点确认，脏知识合法化。  
4. **按人建知识、不按模块建** → 人走茶凉。  
5. **多仓 monorepo 用同一套深度** → 必须 Profile 分域。  
6. **生成 repo-map 却含 `node_modules/target`** → 地图污染。  
7. **用聊天总结代替 OpenAPI/代码** → 契约以生成物为准。  
8. **「类似业务」靠标题相似度** → 应用技术栈+模块标签，别只靠中文句子像不像。  
9. **摸底成功却 gaps 为空** → 往往是幻觉自信；应强制至少 N 个风险/假设待确认。  
10. **为知识库单独立一套权限/服务** → v0 用 Artifact Store 就够，多系统必腐。  
11. **开发迭代快于索引** → L1 必须可再生；手维护 L1 必输。  
12. **省 token 却省掉验收句** → 摸底再准，没有澄清验收仍会偏航（摸底替代不了澄清）。

## 7. 额外建议（针对这一环）

### 7.1 配额制（比「多分桶」更重要）

- L2 认证条目：建议硬顶（如每项目 50；超了必须归档/合并）  
- 每条必须有：`owner`、`last-verified`、`related-paths[]`、`status=active|deprecated`  
- 无 `related-paths` 的条目不得进高信任检索

### 7.2 摸底产出与澄清的接口要硬

`discovery.gaps` → **自动变成** `clarify.questionnaire` 候选题；  
禁止 gaps 写得很帅但拷问阶段另起一套题。

### 7.3 先做「事后学习」再做「事前百科」

每个交付后：对照「最终 diff ∩ 当初 hit-set」算召回 → 只改进检索与地图，**先别扩知识文。**  
这比先写 100 条 lesson 更贴真实迭代。

### 7.4 工具顺序（务实）

```text
rg + 目录地图 + git log/path
  → （可选）语言依赖/符号索引
  → （很后）embedding 补漏
```

### 7.5 与「批量消化」的关系

批量消化的前提不是知识库很大，而是：

- 摸底指标稳定  
- 澄清闸还在  
- L2 瘦且被引用  
- 测试门禁硬  

知识库是 **加速器**，不是 **质量发动机**。质量发动机仍是门禁与契约。

## 8. 若现在就改通路手册：S8 重写草案

**S8a 最小证明：**  
同一需求跑两遍摸底，hit-set 稳定；人为藏一个相关文件名在需求里能被搜到；token 输入 < 设定上限。

**S8b 最小证明：**  
删掉生成的 map，一键再生；CI 可跑。

**S8c 最小证明：**  
最多 N 条认证知识；第二次需求报告出现 knowledgeId；无路径绑定的条目进不了检索。

**明确不做：** 企业知识中台、自动认证、全仓向量必选、手维护完美图谱。

## 9. 总结：接受挑战后的立场

| 陈述 | 结论 |
|------|------|
| 摸底值得做 | **是**，且应尽早做成 **按需检索流水线** |
| 知识库值得做 | **瘦的 L2 是**；胖百科 **否** |
| 图值得做 | **代码/模块图作查询结构是**；故事性知识图谱 **先否** |
| 蓝图 Knowledge 引擎 | **过重**；保留词，落地降维 |
| 原 S8 是否完善 | **否，偏乐观粗粒度**；应用 S8a/b/c |
| 是否切实可行 | **按本文六步+三层+指标，可行**；按「先建完备知识」不可行 |

**一句话：**

> **摸底要学 Aider/搜索/代码索引那种「地图+检索+少读」；  
> 知识库要学 ADR/目录那种「少而认证、可绑定路径、可删除」；  
> 不要学「企业知识中台幻觉」。  
> 可靠来自召回指标与缺口→澄清的硬接口，不来自知识条目数量。**
